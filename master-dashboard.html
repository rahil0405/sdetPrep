Interview Questions — Step 1
Q 01"How does the JavaScript Event Loop handle asynchronous test steps in Playwright?"
Answer: Playwright is built on async I/O. Every browser action returns a Promise. Missing await causes test steps to fire out of order — the assert runs before the click resolves. Mention: call stack, microtask queue, and that Playwright's internal scheduler depends on Promise resolution chains.
Q 02"Write a function to handle a dynamic table where row position changes every refresh."
Answer: Never use nth-child or index-based selectors. Use filter() on the table rows array, matching on a stable attribute like data-id or text content. Demonstrate the difference between stable vs fragile locators.
Q 03"Explain why you would use Promise.all() when waiting for multiple API responses in a test script."
Answer: Sequential await is N× slower for test setup. Promise.all() fires all requests in parallel and resolves when ALL complete. Tradeoff: if one fails, all fail — use Promise.allSettled() when partial success is acceptable.

Interview Questions — Step 2
Q 04"Playwright never needs explicit waits — agree or disagree? Explain with an example."
Answer: Disagree with nuance. Playwright auto-waits for actionability before every action — eliminating 90% of flaky waits. But you still need explicit waits for: custom polling with page.waitForFunction(), network responses with page.waitForResponse(), elements that animate in after a delay. Key insight: Playwright waits for element state, not arbitrary time.
Q 05"Why would you use Page Object Model in a large suite? What breaks without it?"
Answer: Without POM, a single UI change forces updates across potentially 50+ test files. With POM, you update one method in LoginPage.ts and every test inherits the fix. Also: POM makes tests readable business logic. Say: "separation of concerns between test intent and implementation detail."
Q 06"What is your locator selection strategy? How do you avoid flaky selectors?"
Answer: Priority: (1) getByRole() — most resilient, tests accessibility. (2) getByTestId() with data-testid attributes agreed with devs. (3) getByText() for static labels. (4) CSS with stable attributes. Never: nth-child indexes, auto-generated class names, absolute XPaths. SDET insight: "I work with devs to add data-testid attributes during sprint — shift-left quality."

Interview Questions — Step 3
Q 07"Why do you use API calls for test setup instead of navigating through the UI?"
Answer: UI-based setup is 10–30× slower, creates test interdependencies (if UI flow breaks, ALL tests fail), and adds unnecessary failure points. API setup is atomic — it either creates the resource or it doesn't. Also: API setup enables parallel test execution because each worker independently creates/destroys its own test data.
Q 08"Walk me through how you chain an API login call to a UI test."
Answer: Three steps. (1) Use request.post('/api/login') in beforeAll to get a token. (2) Store the token. (3) Set it as a cookie via page.context().addCookies() or inject into localStorage via page.evaluate() so the UI test starts already authenticated. This technique is called session injection.
Q 09"How would you test a 500 error without breaking your real backend?"
Answer: Use route.fulfill() to intercept the specific API call and return a fake 500 response. This lets you test error handling UI without needing the backend to actually fail. This is called network mocking or service virtualisation at enterprise scale.

Interview Questions — Step 4
Q 10"Why run Playwright tests in a Docker container instead of directly on the runner machine?"
Answer: Three reasons. (1) Reproducibility — Docker guarantees identical browser versions, OS libraries, and Node versions on every run. (2) Isolation — each run starts from a clean state. (3) Microsoft's Playwright image ships with all browser dependencies pre-installed. Say: "This ensures CI failures are real test failures, not environment failures."
Q 11"How would you reduce a 20-minute test suite run to under 6 minutes?"
Answer: Playwright sharding via matrix strategy. Split into N shards running in parallel — --shard=1/4, --shard=2/4, etc. 4 shards = roughly 4× speed improvement. Key insight: this only works if tests are properly isolated — no shared state, no sequential dependencies. That's why teardown in Step 3 mattered.
Q 12"A test passes locally but fails consistently on CI. Walk me through debugging this."
Answer: Systematic: (1) Headless vs headed difference — CI runs headless. (2) Missing environment variables or wrong baseURL. (3) Download trace artifact from failed run — open in trace viewer. (4) Browser version mismatch between local and Docker image. (5) Add --retries=1 to identify true flakiness. First tool: trace viewer, not console.log.

Interview Questions — Step 5
Q 13"How does visual regression work and how do you handle intentional UI changes?"
Answer: First run creates a baseline PNG stored in the repo. Every subsequent run pixel-diffs the live screenshot against the baseline — diff above threshold fails the test. For intentional changes: run --update-snapshots, review the diff, commit new baseline. Key insight: "Snapshots are committed to Git so the baseline is versioned alongside the code that produced it."
Q 14"What are Core Web Vitals and why would a QA engineer care about them?"
Answer: LCP (Largest Contentful Paint — main content load speed, target <2.5s), CLS (Cumulative Layout Shift — page stability, target <0.1), FID/INP (interaction responsiveness, <100ms). QA cares because: poor CWV impacts Google ranking (business concern), performance regression is a bug, asserting against a budget in CI catches regressions before production — shift-left principle.
Q 15"Walk me through your entire test framework architecture end to end."
Answer (90 seconds, memorise this): "My framework has five layers: (1) JavaScript utility library for test data processing. (2) Page Object Model in TypeScript — locators private, actions public. (3) API chaining for setup and teardown — test data via POST before UI tests, deleted after. (4) GitHub Actions pipeline on Microsoft's Playwright Docker image, sharded across 4 workers, with Slack failure alerts. (5) Visual regression via Playwright snapshots and Lighthouse performance budget assertions on every push."
