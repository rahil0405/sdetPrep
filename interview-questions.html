Category · JavaScript
JavaScript Questions
These are asked to verify you understand JS deeply enough to write and debug Playwright test code — not to turn you into a frontend developer.
Core Language
JS-01 Mid How does the JavaScript Event Loop work? Why does it matter for Playwright test execution? ▶
// answer
The Event Loop continuously checks the call stack and the task queue. When the call stack is empty, it picks up the next task from the queue. For Playwright: every browser action (click, fill, goto) returns a Promise. The Event Loop resolves these Promises in order. If you forget await, the next line executes before the browser action completes — your assertion runs against a stale DOM state.
  • Call stack: synchronous code runs here
  • Microtask queue: resolved Promises go here — runs before macrotasks
  • Macrotask queue: setTimeout, setInterval
  • Playwright uses Node.js async I/O — all browser interactions are microtasks
🎯Senior signal: mention that Playwright's auto-wait mechanism itself depends on Promise chains resolving correctly — which is why consistent use of async/await is non-negotiable in test code.
JS-02 Mid What is the difference between Promise.all(), Promise.allSettled(), and Promise.race()? When would you use each in a test? ▶
// answer
  • Promise.all(): resolves when ALL promises resolve. Fails fast if any rejects. Use for parallel API setup where ALL resources must exist before the test runs.
  • Promise.allSettled(): resolves after ALL promises settle (pass or fail). Use for teardown — you want all DELETE calls to attempt even if one fails.
  • Promise.race(): resolves with the first promise to settle. Use for timeout patterns — race your test action against a timeout promise.
🎯In your framework: beforeAll uses Promise.all() to create 3 users in parallel. afterAll uses Promise.allSettled() to delete them, ensuring teardown completes even if one delete fails.
JS-03 Hard What is a closure? Give a practical example of where a closure could cause a bug in a Playwright test. ▶
// answer
A closure is a function that retains access to its outer scope's variables even after the outer function has returned.
// Classic closure bug in a loop: for (let i = 0; i < 3; i++) { test(`clicks button ${i}`, async () => { // With var instead of let: all 3 tests would use i=3 // With let: each iteration has its own i binding ✓ await page.click(`button:nth-child(${i})`); }); }
🎯This is why using var in loops with async callbacks is dangerous. let creates block-scoped closures. Always use const or let in test code — never var.
JS-04 Mid Write a function to parse and filter test results from an array of objects — find all failed tests with execution time > 5 seconds. ▶
// answer
const results = [ { name: 'TC001', status: 'passed', duration: 1200 }, { name: 'TC002', status: 'failed', duration: 8500 }, { name: 'TC003', status: 'failed', duration: 3200 }, ]; const getSlowFailures = (results) => results .filter(r => r.status === 'failed' && r.duration > 5000) .map(r => ({ ...r, durationSec: (r.duration / 1000).toFixed(1) + 's' })); // Returns: [{ name: 'TC002', status: 'failed', duration: 8500, durationSec: '8.5s' }]
🎯This pattern comes directly from your Phase 1 work. Say: "This is the same utility pattern I use in my framework's test data processing layer."
JS-05 Mid What is the difference between == and ===? Why should QA engineers always use ===? ▶
// answer
== (loose equality) performs type coercion — "5" == 5 is true. === (strict equality) checks both value and type — "5" === 5 is false.
🎯In test assertions, you always want strict equality. A status code of "200" (string) is not the same as 200 (number). Using == could mask a real bug where an API returns a string status code instead of numeric. Always use === or Playwright's typed matchers like toBe().
JS-06 Hard Explain async/await error handling. What happens if you don't use try/catch in an async test function? ▶
// answer
Without try/catch, an unhandled Promise rejection in an async function propagates up as an unhandled rejection. In Playwright, this causes the test to fail with an unclear error message and potentially skips teardown code (afterEach/afterAll).
// Correct pattern for critical test steps: test('checkout flow', async ({ page }) => { try { await page.goto('/checkout'); await checkoutPage.completeOrder(); } catch (error) { await page.screenshot({ path: 'failure.png' }); throw error; // re-throw so Playwright marks test as failed } });
🎯Playwright actually wraps test functions internally, so unhandled rejections do fail the test. But explicit try/catch lets you capture screenshots and additional diagnostic info before re-throwing.
JS-07 Mid What is destructuring and how do you use it in test data handling? ▶
// answer
// Without destructuring — verbose: const username = users[0].username; const password = users[0].password; // With destructuring — clean: const { username, password, role } = users[0]; // In test data loops: for (const { username, password, role } of users.validUsers) { test(`${role} user can log in`, async () => { await loginPage.loginAs(username, password); }); }
JS-08 Hard What is the difference between null, undefined, and NaN? How would each cause a silent bug in a test assertion? ▶
// answer
  • undefined: variable declared but not assigned. If you destructure a missing key from an API response, you get undefined — and expect(undefined).toBe('active') fails with a confusing error.
  • null: intentional absence of value. An API returning null for a user field when it should return a string is a genuine bug — assert explicitly with expect(field).not.toBeNull().
  • NaN: result of invalid numeric operation. NaN === NaN is false — you must use Number.isNaN() or expect(val).toBeNaN().
🎯Senior signal: always validate API response shape before asserting on specific fields. Use optional chaining (response?.data?.user?.role) defensively.
Category · Playwright Core
Playwright Questions
The deepest technical section. Every question here is asked at mid-to-senior level QA interviews. Know these cold.
Core Mechanics
PW-01 Hard Explain Playwright's auto-wait mechanism in depth. What are actionability checks? ▶
// answer
Before performing any action, Playwright checks that the element passes all actionability criteria. This eliminates most explicit waits.
  • Visible: element has non-zero bounding box, no visibility:hidden or display:none
  • Stable: element not animating — bounding box is stable across two consecutive frames
  • Enabled: element is not disabled or aria-disabled
  • Receives events: element is not obscured by another element at its center point
🎯Actionability is checked continuously until timeout. Default timeout is 30 seconds. You still need explicit waits for conditions Playwright can't detect — like a data attribute changing after an API call, or a specific network response.
PW-02 Hard What is the difference between page.locator(), page.getByRole(), page.getByTestId(), and page.$()? Which should you use and when? ▶
// answer
  • page.locator(css/xpath): flexible, supports any selector. Use for complex queries when semantic locators don't work.
  • page.getByRole(): most resilient — matches ARIA role + accessible name. Also validates accessibility. Use as first choice.
  • page.getByTestId(): matches data-testid attribute. Agreed with devs during sprint. Immune to UI redesigns. Use as second choice.
  • page.getByText(): matches visible text content. Use for static labels. Fragile if text changes with localisation.
  • page.$(): old Playwright API — returns ElementHandle, not Locator. Deprecated pattern. Never use in new code.
🎯Priority order: getByRole > getByTestId > getByText > locator(CSS) > locator(XPath). The further right you go, the more fragile.
PW-03 Hard What is the difference between Locator and ElementHandle in Playwright? Why did Playwright deprecate ElementHandle? ▶
// answer
ElementHandle is a reference to a specific DOM element at a point in time. If the page reloads or the element is replaced, the handle becomes stale and throws errors.
Locator is a lazy query — it re-queries the DOM at the moment of action. If the element is replaced, the Locator finds the new element. This is why Locators are composable, retry-able, and auto-waiting.
🎯The stale element problem is one of the most common Selenium failures. Playwright solved it by making Locator the default — the query is re-executed on every action, not cached.
PW-04 Mid How does the Playwright trace viewer work? What information does it capture? ▶
// answer
Trace viewer is a time-travel debugger. When you run with --trace on, Playwright records a zip file containing:
  • Filmstrip timeline: screenshots at every action with timestamps
  • DOM snapshots: full DOM state before and after each action — clickable in the viewer
  • Network log: all HTTP requests/responses with status codes and payloads
  • Console log: all console.log/error messages during the test
  • Action log: every Playwright call with timing data
🎯This is your answer to "how do you debug CI failures?" — download the trace zip artifact, run npx playwright show-report locally. No need to re-run the failing test.
PW-05 Hard What are Playwright fixtures? How are they different from beforeEach? When would you use one vs the other? ▶
// answer
  • beforeEach: runs setup code before each test in the current describe block. Scoped to a file. Not reusable across test files.
  • Fixtures: dependency injection system. Define once, use in any test file via destructuring from the test object. Composable — fixtures can use other fixtures. Auto-cleanup after each test.
// Fixture — reusable across ALL test files: const test = base.extend({ async loginPage({ page }, use) { await use(new LoginPage(page)); }, async loggedInPage({ loginPage }, use) { await loginPage.loginAs('admin', 'pass'); await use(loginPage); // teardown after use() returns } });
🎯Rule: use beforeEach for simple, file-scoped setup. Use fixtures for anything that is reused across 2+ test files, or that needs guaranteed teardown.
PW-06 Mid How do you handle a dropdown select element in Playwright? What about custom dropdowns built with divs? ▶
// answer
// Native HTML select element: await page.selectOption('#country-select', { label: 'India' }); // or by value: await page.selectOption('#status', 'active'); // Custom div-based dropdown (common in React/Angular apps): await page.click('.dropdown-trigger'); // open it await page.getByRole('option', { name: 'India' }).click(); // select
🎯Custom dropdowns are a common interview live-coding question. The key is: open it first, then select. getByRole('option') works for ARIA-compliant dropdowns.
PW-07 Hard How do you handle multiple browser tabs/windows in Playwright? ▶
// answer
// Wait for new page to open, then switch to it: const [newPage] = await Promise.all([ context.waitForEvent('page'), // listener set BEFORE trigger page.click('a[target="_blank"]') ]); await newPage.waitForLoadState(); await expect(newPage).toHaveURL(/expected-url/);
🎯The listener must be set BEFORE the click that triggers the new tab — this is a common mistake. Promise.all() ensures both run simultaneously.
PW-08 Mid How would you test a file upload in Playwright? ▶
// answer
// Standard file input: await page.setInputFiles('input[type="file"]', './test-data/invoice.pdf'); // Multiple files: await page.setInputFiles('input[type="file"]', [ './test-data/file1.pdf', './test-data/file2.pdf' ]); // Drag-and-drop file upload zone (no input element): await page.dispatchEvent('.drop-zone', 'drop', { dataTransfer: await page.evaluateHandle(...) // construct DataTransfer });
PW-09 Hard What causes flaky tests? List 5 causes and how you fix each in Playwright. ▶
// answer
  • Race conditions: action fires before element is ready. Fix: use Playwright's built-in auto-wait, or page.waitForResponse() for API-triggered state changes.
  • Shared test state: test A creates data that test B depends on. Fix: each test creates and tears down its own data via API.
  • Hardcoded waits: setTimeout or page.waitForTimeout(). Fix: replace with conditional waits (waitForSelector, waitForFunction).
  • Fragile selectors: nth-child, auto-generated classnames. Fix: use data-testid attributes agreed with developers.
  • Timing differences (CI vs local): CI machines are slower/headless. Fix: increase timeouts in CI config, use --retries=1 to identify true flakiness vs genuine failures.
🎯A flaky test is worse than no test — it destroys confidence in the entire suite. The SDET's job is to eliminate flakiness systematically, not mask it with retries.
PW-10 Senior How does Playwright compare to Selenium? Why would you choose Playwright for a new project in 2024? ▶
// answer
  • Auto-wait vs explicit waits: Playwright's actionability checks eliminate 90% of flaky wait code that plagues Selenium suites.
  • Modern async: Playwright is built for async/await from the ground up. Selenium's architecture predates Promises.
  • Built-in trace viewer: no equivalent in Selenium. Single biggest debugging advantage.
  • Network interception: route.fulfill() is native. Selenium requires external proxy setup (BrowserMob).
  • Single package: Playwright installs browsers automatically. Selenium requires separate WebDriver management (ChromeDriver versions).
  • Parallel isolation: each Playwright test gets its own browser context by default. Selenium shares sessions unless explicitly managed.
🎯If the interviewer asks "but Selenium is still widely used" — agree, and say: "For large organisations with existing Selenium investment, migration cost is real. For new projects, Playwright is the clear choice for developer experience and test reliability."

Architecture
POM-01 Senior Walk me through your entire test framework architecture end to end. (The master question) ▶
// your 90-second answer — memorise this
"My framework has five layers. Layer 1 is a JavaScript utility library for test data processing — filter, map, reduce over user fixtures, feeding every test in the suite. POM-02 Hard How do you handle test data management in your framework? What is data-driven testing? ▶
// answer
Test data lives in JSON files in the test-data/ folder, completely separate from test logic. Data-driven testing means one test function runs multiple times with different input datasets — each row of data produces a separate test case.
// Data-driven pattern from your framework: for (const user of users.invalidUsers) { test(`rejected: ${user.username}`, async ({ page }) => { await loginPage.loginAs(user.username, user.password); await expect(page).not.toHaveURL(/inventory/); }); }
🎯Adding a new test case is now a one-line JSON change — no code change needed. This is the scalability benefit of separating data from logic.
POM-03 Senior How would you design a framework for a project that has both web and mobile testing requirements? ▶
// answer
  • Shared layer: business logic, test data, API utilities are device-agnostic — live in a shared/ folder
  • Separate POM layers: web/pages/ and mobile/screens/ — different interaction patterns but same data
  • Playwright for web, Appium or Detox for mobile — separate toolchains, shared test data and fixtures
  • Unified reporting: both suites output to the same Allure or Extent report via CI
🎯If mobile is out of scope for your current role, be honest: "My current framework covers web. For mobile, I understand the architecture would extend the data and API layers while replacing the browser interaction layer with Appium."
POM-04 Hard What is the test pyramid? How does it influence how you structure your Playwright suite? ▶
// answer
The test pyramid: many unit tests at the base, fewer integration tests in the middle, few E2E tests at the top. E2E tests are slow and expensive — they should cover critical user journeys only.
  • In your Playwright suite: keep E2E tests to happy paths and critical failure scenarios (not every edge case)
  • Edge cases: validated at unit test level with Jest/Vitest — fast, no browser
  • API tests: sit in the integration layer — faster than full E2E, test business logic directly
🎯Your Phase 3 API tests are the integration layer. Your Phase 2 UI tests are the E2E layer. You've built the pyramid without naming it that way — now name it.
POM-05 Hard How do you handle test environment configuration — different baseURLs for dev, staging, production? ▶
// answer
// playwright.config.ts — environment-aware config: const ENV = process.env.TEST_ENV || 'staging'; const envConfig = { staging: { baseURL: 'https://staging.myapp.com' }, production: { baseURL: 'https://myapp.com' }, local: { baseURL: 'http://localhost:3000' }, }; export default defineConfig({ use: { baseURL: envConfig[ENV].baseURL } }); // Run against production: TEST_ENV=production npx playwright test
🎯Environment variables are also set in GitHub Actions secrets — TEST_ENV: staging in the workflow YAML. Never hardcode URLs.
POM-06 Senior What is shift-left testing? How does your framework implement it? ▶
// answer
Shift-left means moving testing earlier in the development lifecycle — catching bugs when they're cheapest to fix, not after deployment.
  • data-testid attributes: I collaborate with devs during sprint to add these before I write tests — testing considerations are baked into the build
  • API tests run first: contract testing of APIs before UI tests run — if the API is broken, you know immediately
  • PR triggers: CI runs on every pull request — bugs caught before code merges to main
  • Performance budgets: Lighthouse fails the pipeline if CWV degrades — performance regression caught before reaching users
Category · API Testing
API Testing Questions
Both API testing as a primary concern, and API chaining as a test setup pattern. Know the difference and when each applies.
API Fundamentals
API-01 Mid What HTTP status codes should you assert in API tests? What does each range mean? ▶
// answer
  • 2xx Success: 200 (OK), 201 (Created — assert after POST), 204 (No Content — assert after DELETE)
  • 3xx Redirect: 301 (Moved Permanently), 302 (Temporary redirect) — usually follow automatically
  • 4xx Client Error: 400 (Bad Request), 401 (Unauthorized — missing auth), 403 (Forbidden — insufficient permissions), 404 (Not Found), 422 (Validation error)
  • 5xx Server Error: 500 (Internal Server Error), 503 (Service Unavailable) — mock these with route.fulfill()
🎯Always assert both the status code AND the response body shape. A 200 with an empty data array is a bug, not a success.
API-02 Hard What is the difference between authentication and authorisation in API testing? ▶
// answer
Authentication = who are you? (login, token generation). Authorisation = what are you allowed to do? (role-based access).
  • Test authentication: POST /login returns a token for valid credentials, 401 for invalid
  • Test authorisation: Admin token can DELETE /users, Viewer token gets 403 on DELETE /users
  • In your framework: you extract the token from the login API response and pass it in headers for subsequent requests
🎯Common bug: API correctly checks authentication but skips authorisation checks — a Viewer can delete records they shouldn't. This is a security test, not just a functional test.
API-03 Hard How do you validate the schema of an API response? Why isn't just checking the status code enough? ▶
// answer
const response = await request.get('/api/users/1'); expect(response.status()).toBe(200); const body = await response.json(); // Check shape, not just status: expect(body).toHaveProperty('id'); expect(body).toHaveProperty('email'); expect(typeof body.id).toBe('number'); expect(body.email).toMatch(/^[^\s@]+@[^\s@]+\.[^\s@]+$/);
🎯Status 200 with a null body, missing fields, or wrong data types is a contract violation — the UI will break when it tries to render the data. Schema validation catches these.
API-04 Mid Why do you use Playwright's built-in request context instead of Axios or node-fetch for API testing? ▶
// answer
  • Zero additional dependencies: request is built into @playwright/test — no extra packages
  • Shares browser context: cookies and storage state from the browser context flow into API calls automatically
  • Integrated reporting: API calls appear in trace viewer and HTML report
  • Same async pattern: consistent async/await syntax with the rest of your Playwright code
  • Built-in retry: can leverage Playwright's retry mechanism
API-05 Senior What is contract testing? How does it differ from API testing? ▶
// answer
API testing validates that an API works correctly. Contract testing validates that the API's interface (the "contract") hasn't changed in a way that breaks its consumers.
  • Tools: Pact.io is the industry standard for consumer-driven contract testing
  • Use case: Microservices — Service A consumes Service B's API. If Service B changes a field name, contract tests catch it before deployment.
  • Different from API testing: contract testing is about the interface agreement, not the business logic
🎯If asked about contract testing, acknowledge it as a concept and be honest about your experience level. Mentioning Pact.io shows awareness without overclaiming.
API-06 Hard How would you test pagination in an API? What edge cases matter? ▶
// answer
  • Happy path: first page returns correct count, has next page link/cursor
  • Last page: no next page link, correct item count (may be less than page size)
  • Empty results: page=1 returns empty array, not 404
  • Out of range: page=999 returns empty array, not 500
  • Page size validation: page_size=0 or negative should return 400 or use default
  • Consistency: total count in metadata matches actual records returned across pages
API-07 Mid What is the difference between route.fulfill() and route.abort() in Playwright? ▶
// answer
  • route.fulfill(): intercepts the request and returns a custom response. Use to mock API responses (fake data, error codes, slow responses).
  • route.abort(): intercepts and kills the request — simulates network failure, DNS failure, or timeout. Use to test how the UI handles complete connectivity loss.
  • route.continue(): lets the request proceed normally but allows you to modify headers/body.
// Simulate offline mode: await page.route('**/*', route => route.abort('failed')); await page.goto('/'); // Assert offline banner appears
API-08 Senior How do you handle flaky API calls in test setup? What if the external API is slow or unreliable? ▶
// answer
  • Retry with backoff: wrap API calls in a retry utility — attempt 3 times with exponential backoff
  • Timeout configuration: set explicit timeout on request context, not the default
  • Mock instead: if the external API is truly unreliable, mock it with route.fulfill() in CI — only hit real API in smoke test suite
  • Health check: add a beforeAll that verifies the API is reachable before running the full suite
🎯Senior signal: recognise the difference between test infrastructure reliability (your problem to solve) and application reliability (developer's problem to solve). Don't mask app bugs by retrying too aggressively.
Category · CI/CD & Docker
CI/CD Questions
Most QA candidates can't answer these. You built a working pipeline — this is your competitive advantage.
Pipeline & Docker
CI-01 Hard Explain the difference between fail-fast: true and fail-fast: false in GitHub Actions matrix strategy. When would you use each? ▶
// answer
  • fail-fast: true (default): if any matrix job fails, GitHub Actions cancels all other running jobs immediately. Saves compute time — good when you just want to know if anything failed.
  • fail-fast: false: all matrix jobs run to completion regardless of failures. Use for test suites — you want the full picture of what failed, not just the first shard that broke.
🎯In your framework: fail-fast is false for the test job. This means if shard 2 fails, shards 1, 3, 4 still complete — you get a comprehensive failure report, not a partial one.
CI-02 Hard What is the difference between npm install and npm ci? Why does CI use npm ci? ▶
// answer
  • npm install: installs packages, updates package-lock.json if versions differ. Can produce different dependency trees on different machines.
  • npm ci (clean install): deletes node_modules first, installs exactly what's in package-lock.json, fails if lock file doesn't match package.json. Deterministic — same tree every time. 2× faster than npm install.
🎯npm ci is CI-safe because it guarantees reproducibility. If a developer accidentally updates a package locally but doesn't commit the lock file, npm ci will fail the pipeline, catching the inconsistency.
CI-03 Senior What is a GitHub Actions cache? How does it speed up your Playwright pipeline? ▶
// answer
actions/cache saves and restores directories between workflow runs. Without caching, npm ci downloads all packages from scratch on every run (slow). With caching, node_modules is restored from cache if package-lock.json hasn't changed.
- uses: actions/setup-node@v4 with: node-version: '20' cache: 'npm' # This enables caching automatically
🎯Cache hit: npm ci skips downloading and runs in ~5 seconds. Cache miss (lock file changed): full install, maybe 60 seconds. Cache key is a hash of package-lock.json.
CI-04 Hard What is the if: always() condition on the artifact upload step? Why is it important? ▶
// answer
By default, a step only runs if all previous steps succeeded. if: always() overrides this — the artifact upload runs regardless of whether the test step passed or failed.
🎯Without if: always(), when tests fail, the upload step is skipped — and you have no report to investigate. This is the most common rookie CI mistake. The report is most valuable precisely when tests fail.
CI-05 Mid What is workflow_dispatch in GitHub Actions? When would you use it? ▶
// answer
workflow_dispatch adds a "Run workflow" button in the GitHub Actions UI — allowing manual trigger of the pipeline without a code push.
  • Use case: run smoke tests against production after a deployment
  • Use case: trigger a full regression suite on demand before a release
  • Can accept input parameters — useful for targeting a specific test tag or environment
CI-06 Hard How would you configure your pipeline to only run tests affected by a code change, rather than the full suite on every push? ▶
// answer
  • paths filter: GitHub Actions on.push.paths — only trigger if specific files changed
  • tags/grep: Playwright's --grep flag runs only tests matching a pattern — tag critical tests with @smoke, run only those on PR, full suite on merge to main
  • Test impact analysis: advanced — tools like Launchable.io use ML to predict which tests are likely to fail given the changed files
on: push: paths: - 'src/checkout/**' # Only run if checkout code changed - 'tests/e2e/**'
CI-07 Senior What would you add to this pipeline to make it truly enterprise-grade? ▶
// answer
  • Allure reporting: rich, historical test reports with trend analysis and flakiness metrics
  • Test retry on failure: --retries=2 in CI config to distinguish genuine failures from infrastructure flakiness
  • Separate smoke suite: 10 critical tests tagged @smoke — run on every PR in under 2 minutes
  • Scheduled regression: full suite nightly on a cron schedule
  • Environment matrix: run against staging AND production with different test sets
  • Security scanning: add SAST step (npm audit) alongside test execution

Visual Regression & Performance
The differentiator layer. Most candidates don't have this. You do — own it.
Visual & Performance
VP-01 Hard Why do you commit snapshot baselines to Git instead of storing them externally? ▶
// answer
  • Version parity: baseline is version-controlled alongside the code that produced it — you always know which code version corresponds to which visual baseline
  • PR diff visibility: when baselines are updated, the PNG diff is visible in the PR — design reviews can happen in code review
  • CI consistency: CI always uses the same baseline as the code being tested — no external service dependency
  • Audit trail: Git history shows every visual change with who approved it and why
VP-02 Mid How do you handle false positives in visual regression tests — cases where tests fail but the UI looks correct? ▶
// answer
  • animations: 'disabled' in config — animations cause pixel differences between runs
  • threshold config: set maxDiffPixelRatio or maxDiffPixels to allow minor anti-aliasing differences
  • mask dynamic areas: mask elements with dynamic content (timestamps, ads, user avatars) using the mask option
  • Font rendering: always run visual tests on the same OS — font rendering differs between macOS and Linux
await expect(page).toHaveScreenshot('home.png', { mask: [page.locator('.dynamic-timestamp')], maxDiffPixelRatio: 0.02 // 2% pixel difference allowed });
VP-03 Hard What is Largest Contentful Paint (LCP) and how would you diagnose an LCP regression? ▶
// answer
LCP measures when the largest visible element in the viewport finishes rendering — typically a hero image or headline. Target: under 2.5 seconds. Over 4 seconds is poor.
  • Common causes of LCP regression: large unoptimised hero image added, lazy loading applied to LCP element, render-blocking CSS/JS added, server response time increased
  • Diagnosis: Lighthouse report shows exactly which element is the LCP element and what caused the delay (resource load time, render delay, time to first byte)
  • In your framework: if Lighthouse CI fails the performance budget, the pipeline fails — team investigates before merging
VP-04 Mid What is Cumulative Layout Shift (CLS)? What causes it and how do you assert against it? ▶
// answer
CLS measures how much visible content shifts unexpectedly during page load. A score of 0 is perfect, above 0.1 is "needs improvement", above 0.25 is poor.
  • Causes: images without explicit width/height, ads injecting content, web fonts causing FOUT (flash of unstyled text), dynamically injected elements
  • Assert in your framework: Lighthouse thresholds config — { "cumulative-layout-shift": { "maxScore": 0.1 } }
  • Why QA cares: high CLS means users accidentally click wrong elements because content moved — directly impacts conversion rates
VP-05 Senior How would you build a performance regression alerting system — flag if performance degrades between releases? ▶
// answer
  • Run Lighthouse on every CI build, save scores to a JSON artifact
  • Compare current run's scores against previous run using a custom script in the pipeline
  • If any score drops by more than 5 points, fail the pipeline and send a Slack alert with the delta
  • For enterprise: tools like Calibre or SpeedCurve track performance trends over time with dashboards
🎯This is a "design a system" answer — you don't need to have built this, but you need to describe the architecture clearly. It shows systems thinking.
VP-06 Mid What is the accessibility score in Lighthouse and why should a QA engineer care about it? ▶
// answer
Lighthouse's accessibility score checks against WCAG guidelines — proper ARIA labels, colour contrast, keyboard navigation, alt text on images.
  • Legal requirement in many markets — WCAG 2.1 AA compliance is legally mandated for government and financial services sites in India and globally
  • Business impact: poor accessibility excludes users with disabilities — estimated 15% of population
  • Bonus: asserting getByRole() in your Playwright tests simultaneously validates accessibility — your locator strategy and a11y testing are the same work
🎯Mention accessibility as a quality dimension, not just a compliance checkbox. It differentiates you from candidates who only think about functional correctness.

System Design for QA
SC-01 Senior You join a company that has no automation. The team does everything manually. How do you build automation from scratch in 90 days? ▶
// answer framework
  • Days 1–14 (Discover): map the current manual test suite, identify the 20% of tests that catch 80% of bugs, instrument DevTools to understand the app's real network and DOM patterns
  • Days 15–30 (Foundation): set up Playwright + TypeScript + POM skeleton, implement CI pipeline with GitHub Actions, establish data strategy (JSON fixtures + API setup)
  • Days 31–60 (Core suite): automate the critical-path tests identified in phase 1 — login, checkout, key user journeys. Target: 20 tests covering 80% of regression risk
  • Days 61–90 (Expand + report): add visual regression for key UI components, configure Slack alerting, present metrics to stakeholders — tests run time, bugs caught, manual testing hours saved
🎯The differentiator: start with discovery, not coding. Interviewers want to see that you understand ROI, not just technical execution.
SC-02 Senior Your CI pipeline is taking 45 minutes to run. The team is complaining. How do you reduce it to under 10 minutes? ▶
// systematic approach
  • Profile first: identify the slowest tests using the HTML report's duration column — fix the top 10% of slow tests first
  • Sharding: split suite into 4–8 parallel workers using Playwright's --shard flag
  • API setup vs UI setup: replace any remaining UI-based setup with API calls — 10x faster per test
  • Smoke + full separation: run only @smoke tagged tests on PR (5 min), full regression nightly (45 min is fine overnight)
  • Remove redundancy: audit for duplicate tests or tests that cover the same scenario at multiple layers
  • npm ci caching: ensure node_modules is cached between runs
SC-03 Senior A test was passing for 3 months. Today it fails on CI but passes locally. Walk through your complete debugging process. ▶
// debugging process
  • Step 1: Download the trace artifact from the failed CI run — open in trace viewer. Look at the exact DOM state and network activity at failure point.
  • Step 2: Check if any dependencies changed — package.json, Docker image version, environment variables
  • Step 3: Check if the application changed — what was deployed around the time failures started? Talk to the dev team.
  • Step 4: Run with --headed locally in the same environment conditions (headless, same viewport, same network)
  • Step 5: Check for timing — add --retries=1 to see if it's intermittent
  • Step 6: Check for test isolation — did another test that runs before this one change shared state?
🎯Most interviewers want to hear: trace viewer first, talk to devs second, never add sleep() as a fix.
SC-04 Senior How do you measure the ROI of test automation? What metrics do you present to management? ▶
// answer
  • Time saved: hours of manual regression per sprint × cost per hour vs automation maintenance cost
  • Bug detection speed: average time from code commit to bug detection (before: next QA cycle = days; after: CI run = minutes)
  • Regression coverage: % of regression test suite automated — trend over time
  • Flakiness rate: % of test runs with at least one flaky test — lower is better, track monthly
  • Production defect rate: bugs that escaped to production — should decrease as automation coverage increases
🎯Management cares about business outcomes, not test counts. Frame everything in time, money, and risk. "Our CI pipeline catches 85% of regressions within 6 minutes of a commit" is more compelling than "we have 200 tests."
